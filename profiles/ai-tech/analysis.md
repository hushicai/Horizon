# 评估目标

判断一条内容对**做 AI 应用的工程师**是否有可复用的技术价值：能否帮助他在 `match.md` 全栈体系（自底向上 L1–L6 + 横切 X1–X3）的某一层里把系统建得更稳、更准、更省、更安全——讲清机制、给出可复核证据、能迁移到实际项目。

# 评分标准

- **9–10：必读。** 给出可直接复用的架构、实现或工程结论，含清晰机制、代码 / 实验 / 数据支撑；对下列任一环节有实质推进，能直接指导落地或复现：模型选型与服务、数据与文档工程、知识/图谱/本体、检索与 RAG、上下文与记忆、循环与目标、动态动作流编排、多智能体与协议、工具与沙箱、多模态交互、Agentic UX、评测与可观测、LLMOps 与成本、安全治理合规。
- **7–8：值得精读。** 有明确的实现细节、实测数据、权衡取舍或生产踩坑；即使不是全新，也能显著加深理解或修正既有做法（含重要模型能力变化及其对应用的影响）。
- **5–6：可作素材。** 主题相关但偏概述、细节不足、证据薄弱，或需与其他材料合并后才有价值；纯 benchmark 数字但无工程含义者落在此档。
- **3–4：低优先级。** 重复已有结论、只有观点无证据、教程式步骤但无原理，或主要是版本更新说明。
- **0–2：噪音。** 与 AI 应用开发全栈及模型无关、标题党、无法验证的性能宣称、纯营销或纯资讯。

# 评估要求

- 优先依据官方文档、代码仓库、可复现实验或一手工程复盘；区分**已验证结果、作者主张、演示、预告与第三方评论**。
- 涉及性能 / 效果 / 成本 / 循环步数的说法，保留基线、数据集、指标、测试条件与限制；没有基线或数字时不要按高分处理。
- 先判断内容落在哪一层哪一子域（L1 模型 / L2 数据知识 / L3 上下文检索 / L4 智能体系统 / L5 应用交互 / L6 交付生态 / X1 评测可观测 / X2 可靠性运维 / X3 安全治理），据此评估其**对应用开发的可用性**：能落地、能复用、能避坑的给高分，纯理论或纯资讯给低分。数据/文档工程、检索、编排、评测、UX、运维、安全等"非模型"层与模型层同等对待，不因不涉及模型而降分。
- 模型类内容关注其**能力边界与工程含义**（上下文、延迟、成本、部署、微调、兼容性、结构化输出），而不只是「又发了新模型」。
- 不因作者或公司知名度、社交热度加分；不把「新版本发布」本身当作技术突破。
- 给出 3–5 个具体主题标签（优先使用中英文关键词，如 `chunking`、`embedding`、`GraphRAG`、`ontology`、`agent-loop`、`replanning`、`goal-hijacking`、`trajectory-eval`、`context-engineering`、`rerank`、`A2A`、`structured-output`、`llmops`、`ai-gateway`、`guardrails`、`agentic-ux`、`test-time-compute`、`kill-switch`）。
